이 절은 "성과계획서·성과보고서 PDF 원문을 수기 구조화 데이터와
대조하는 작업"을 다른 부처·다른 연도로 확장할 때 그대로 따라 할 수
있는 절차와, 1부에서 실제로 겪은 함정을 모은 것입니다.

### 사전 준비 (구현 시작 전)

1. `docs/PROJECT_PLAN.md`, `docs/WORK_LOG.md`, `docs/work_tracker.json`
   을 먼저 확인해 이미 비슷한 작업이 있었는지 확인합니다(중복 구현
   방지).
2. 대상 PDF의 페이지 수·연속 구간·해상도를 원본과 대조하고, **어느
   페이지가 이미지 표(텍스트 레이어 없음)인지, 어느 페이지가 회전
   표인지**를 먼저 육안으로 확인합니다(0-1 사례).
   - 이미지 표라고 바로 OCR로 넘어가지 말고, **같은 문서의 다른
     요약/총괄 페이지가 텍스트 레이어를 갖고 있는지**부터 확인합니다

   사유를 정리해 둔 표)가 있는지 먼저 찾습니다. 있다면 "왜 바뀌었는지"
   를 추정하지 말고 이 표를 직접 파싱하는 것을 최우선으로 설계합니다
   (보완2·3 교훈 — 추정으로 시작했다가 나중에 틀린 것으로 판명된
   사례가 있었음).
4. `docs/CURSOR_MSS_PERFORMANCE_PDF_RECONCILIATION_PROMPT.md`를
   템플릿으로 복제해 해당 부처용 실행 계약(입력 경로, 모집단, 추출
   필드, 매칭 규칙, 판정값, 출력 형식, 완료 조건, 임의 판단 중단
   조건)을 먼저 문서로 확정합니다.
5. `docs/work_tracker.json`/`docs/WORK_TRACKER.md`에 대응 작업 ID가
   없으면 구현 시작 전에 먼저 추가합니다(`work_tracker_hook.py add`).

### 표준 절차

```text
1. 지표명 매칭
   정규화(공백·줄바꿈·괄호·원문자숫자·문장부호 제거) 정확 일치를
   우선. 명칭이 달라도 "변경 사항"표에 근거가 있으면 동일 지표로
   연결하되, 문자열 유사도만으로는 절대 확정하지 않음.

2. 같은 연도 안에서 지표명이 중복되는지 먼저 확인
   (보완4 사례). 텍스트 검색 기반 매칭은 "첫 번째 일치"만 찾는
   구조적 한계가 있으므로, 매칭 전에 지표명 중복을 자동 탐지하는
   단계를 반드시 넣음.

3. 페이지 근거를 3중으로 기록
   분리 PDF 페이지(`split_pdf_page`) / 원본 PDF 페이지
   (`source_pdf_page`) / 인쇄 쪽번호(`printed_page`, 없으면 null).
   "변경 사항"표처럼 인쇄 쪽번호가 원래 없는 문서도 있으므로, 항상
   채워지는 분리·원본 페이지를 근거 추적의 기본으로 삼음.

4. 숫자는 원문 문자열과 변환값을 모두 보존
   `*_raw`(쉼표·%·공백 제거 전)와 `*_numeric`을 분리. 공식 값
   (예: 공식 달성률)을 계산값으로 절대 덮어쓰지 않음.

5. OCR은 항상 사람 검토 필요로 남김
   OCR로 값을 찾아도 자동 확정(EXACT_MATCH)하지 않음. PUA 글리프
   등 폰트 매핑 실패로 텍스트 검색이 안 되는 경우도 "없음
   (PDF_NOT_FOUND)"으로 단정하지 말고 OCR 재시도 후에도
   OCR_REQUIRED로 사람 확인을 요구함.

6. 1차 판정 후 "얼마나 바뀌었는지"부터 정량화
   "왜 바뀌었는지"(사유)는 원문 근거 없이는 알 수 없지만, "얼마나"는
   이미 추출한 두 숫자의 단순 차이이므로 먼저 계산해 제공(보완1).

7. "왜 바뀌었는지"는 추정보다 원문의 변경사항표를 먼저 찾아 확정
   추정이 꼭 필요하면 코드/데이터가 아니라 문서에만 "추정, 확정
   아님"으로 명확히 분리해 기록(보완2). 나중에 원문 근거가 나오면
   즉시 교체(보완3).

8. 검수 워크플로우를 분리
   - 사람이 봐야 할 파일·쪽수는 여러 컬럼에 흩어두지 말고 한 줄
     안내문으로 조합해서 보여줌(`review_instruction` 패턴).
   - 검수 확정은 파이프라인이 자동 생성하지 않는 별도 CSV로 관리
     (`reviewer`/`review_status`/`review_note`/`review_confirmed_at`).
     판정 컬럼(`overall_reconciliation_status` 등)은 검수 확정과
     별개로 유지하고, 검수 CSV가 원본 판정값을 덮어쓰지 않게 함.
   - 에이전트가 먼저 원문 페이지를 렌더링해 대조하고, 실제로 사람
     판단이 필요한 것만 걸러 보고(보완7·8 방식 — "뭘 봐야 하냐"고
     계속 되묻지 않음).

9. 라벨 재분류는 조건을 코드로 명시하고 반례 테스트로 검증
   검수로 "오류가 아님"이 확인됐다고 즉시 라벨을 바꾸지 말고, 재분류
   조건(예: 변경사항표 숫자와 정확히 일치)을 코드로 명시하고, 조건을
   만족하지 않는 반례 케이스도 테스트로 함께 검증(보완9).

10. 매 단계마다 pytest + ruff + WORK_LOG 기록 + work_tracker 갱신
    구현 완료 → 실제 데이터 재실행 → 행 수/기본키/해시 불변 확인 →
    테스트 통과 → 문서 기록까지 끝나야 완료로 처리(AGENTS.md 24절).
```
