# 프로젝트 폴라리스

- 상태: 사용자 합의 확정
- 기준일: 2026-07-31
- 수기 기준선 동결 목표: 2026-08-03
- 선택형 LLM 모듈 Go/No-Go: 2026-08-05
- 최종 제출일: 2026-08-09

이 문서는 구현 편의보다 프로젝트 목적을 우선하기 위한 최상위 판단 기준입니다.
새 기능, 분석기준, 데이터 범위 또는 화면을 설계할 때 먼저 이 문서와 맞는지
확인합니다. 목적이 바뀌면 코드를 먼저 고치지 않고 이 문서의 결정부터 갱신합니다.

## 1. 북극성

> 여러 부처의 공개 성과·예산·집행자료를 같은 절차로 연결하여, 재정·성과관리
> 실무자가 긴 성과계획서와 성과보고서를 처음부터 모두 읽지 않고도 추가 설명이
> 필요한 세부사업을 좁히고 무엇부터 원문 검토할지 근거와 함께 결정하도록 돕습니다.

이 프로젝트는 성과관리 기반 재정평가 업무의 AX 의사결정 보조도구입니다.
대시보드와 LLM은 목적이 아니라 실무자의 탐색·검토 시간을 줄이는 수단입니다.

## 2. 출발점

성과계획서와 성과보고서는 한 부처 문서도 통상 수백 쪽에 이릅니다. 예산안을
검토하는 실무자가 모든 줄글과 표를 먼저 읽은 뒤 성과·집행·예산 관계를
수작업으로 확인하는 것은 시간이 많이 듭니다.

이 프로젝트는 원문 검토를 없애지 않습니다. 먼저 구조화된 신호와 근거를 이용해
검토범위를 좁힌 뒤, 실제 판단이 필요한 후보의 원문만 빠르게 확인하게 합니다.

## 3. 사용자와 의사결정 시점

### 3.1 주 사용자

- 재정·성과관리 실무자
- 예산안 검토와 성과관리 자료를 함께 보는 분석 담당자

경진대회 심사위원과 일반 국민은 주 사용자가 아닙니다. 심사위원에게는 실무자가
이 도구를 어떻게 사용하는지와 어떤 분석적 발견을 얻었는지를 시연합니다.

### 3.2 목표 운영 시점

장기 운영 목표는 성과계획서 제출과 예산안 확정 사이의 검토기간입니다.

입력은 다음을 기본으로 합니다.

- 과거 성과계획서
- 과거 성과보고서
- 가장 최근 성과계획서
- 과거 및 현재 가용 예산·집행·결산자료
- 최신 연도 성과보고서는 시차상 아직 없을 수 있음

이 자료를 이용해 어느 세부사업부터 예산 조정 필요성을 검토할지 좁힙니다.
실제 증액·감액 결정에는 정책 우선순위, 사업 필요성, 부처 소명과 추가자료가
필요하므로 시스템이 자동 처분하지 않습니다.

## 4. 지원하는 단 하나의 의사결정

> 제한된 검토시간 안에서 어떤 세부사업의 성과·집행·예산 근거와 원문부터
> 확인할 것인가?

결과는 다음 의미를 갖습니다.

- 점검 우선순위
- 추가 설명 필요
- 원문 검토 필요
- 집행관리 확인
- 성과지표 재설계 검토
- 사업구조 변경 여부 확인

다음 의미로 사용하지 않습니다.

- 실패·낭비 사업 자동 판정
- 삭감·폐지 대상 자동 결정
- 증액 필요 사업 자동 결정
- 정책효과 또는 인과관계 확정

## 5. 분석 계층과 최종 한 행

### 5.1 최종 검토대기열

최종 화면과 제출용 후보표의 한 행은 다음을 목표로 합니다.

```text
부처 × 세부사업 × 회계연도
```

### 5.2 프로그램 성과의 사용

성과계획서·성과보고서의 성과지표가 프로그램 단위인 경우 프로그램 성과를
세부사업의 성과로 임의 귀속하지 않습니다.

점검대기열은 다음의 2단계 계층을 유지합니다.

1. 프로그램 성과·재정 신호로 먼저 볼 프로그램 맥락을 찾습니다.
2. 그 프로그램 안에서 세부사업 자체의 예산·집행·사업구조 신호로 최종
   검토순서를 제시합니다.

프로그램 성과는 세부사업 행에 `상위 프로그램 맥락`으로 표시하지만
`세부사업 성과점수`로 표시하지 않습니다.

### 5.3 제공할 화면

- 전체 부처 세부사업 점검대기열
- 선택한 부처 내부 세부사업 점검대기열
- 프로그램 맥락과 소속 세부사업 드릴다운
- 후보별 성과지표·예산·집행·데이터품질·원문근거 카드

전체 순위는 서로 다른 사업의 절대 효과성 비교가 아니라 전 부처 검토작업의
순서입니다.

## 6. 적용 범위와 확장 계약

### 6.1 최종 목표

전체 중앙재정사업에 적용 가능한 범용 분석틀을 구축합니다.

### 6.2 2026년 경진대회 실증 범위

현재 원본 성과데이터가 준비된 다음 4개 부처를 완결된 실증 범위로 사용합니다.

- 고용노동부 `019`
- 보건복지부 `075`
- 중소벤처기업부 `102`
- 과학기술정보통신부 `162`

행정안전부 표본은 원본 데이터 계약과 품질이 정리되기 전까지 이번 핵심
산출물에 포함하지 않습니다.

### 6.3 부처 확장 완료조건

새 부처를 추가할 때 분석 코드를 수정하지 않습니다.

```text
부처 성과자료 투입
+ 부처코드 설정
→ 동일 스키마 정규화
→ 재정자료 연결
→ 전체·부처별 순위 재계산
→ 대시보드 자동 노출
```

부처 수나 부처명을 소스코드, 경로명, 화면 선택지에 하드코딩하지 않습니다.

## 7. 모듈 경계

각 모듈은 독립적으로 검증하고 표준 출력계약으로 연결합니다.

### 모듈 A. 성과문서 구조화

```text
성과계획서·성과보고서
→ 문서 추출
→ 구조화 후보
→ 사람 검수
→ 승인된 성과 데이터셋
```

- 현재: 수기로 구조화·검수한 파일을 입력 어댑터로 사용
- 향후: LLM 추출 모듈을 같은 출력 스키마의 입력 어댑터로 추가
- 수기 입력과 LLM 입력을 바꿔도 이후 분석 코드는 바뀌지 않아야 함

### 모듈 B. 재정데이터 구축

```text
열린재정 API·공식 파일
→ 원본 보존
→ 예산·집행·결산 정규화
→ 세부사업 재정 마스터
```

### 모듈 C. 계층 연결

```text
승인된 성과 데이터셋
+ 세부사업 재정 마스터
→ 프로그램 맥락과 세부사업 재정근거 연결
```

### 모듈 D. 점검 우선순위 분석

```text
데이터 품질 분리
→ 신호 유형화
→ 복수 시나리오
→ 순위 안정성
→ 세부사업 검토대기열
```

### 모듈 E. 검수·탐색 대시보드

```text
검증 완료 산출물
→ 전체·부처별 탐색
→ 근거 확인
→ 원문 검수
→ 결과 다운로드
```

대시보드 안에서 원천 전처리나 확정 분석을 다시 계산하지 않습니다.

## 8. LLM과 Human-in-the-loop

LLM API 키 보유 여부와 관계없이 2026-08-03 수기 기준선 동결 전에는 실시간
LLM 파이프라인을 핵심 경로에 넣지 않습니다.

현재 수기 성과데이터의 스키마를 향후 LLM 모듈의 합격 출력계약으로 사용합니다.
LLM은 문서에 있는 값과 근거 위치만 추출하며 확인할 수 없는 값은 생성하지
않습니다. LLM의 추정은 지표유형·검수필요 여부·신뢰도 같은 후보값에만
허용하고 목표치·실적치·단위·예산액을 추정하지 않습니다.

향후 LLM 모듈은 최소한 다음을 보존합니다.

- 문서명과 문서유형
- 회계연도
- 부처·프로그램 식별정보
- 성과지표명·목표·실적·단위·지표방향
- 원문 페이지와 근거문장
- 추출 신뢰도와 오류유형
- 사람 검수상태·수정값·검수이력

### 8.1 로컬 우선 처리

API로 전체 PDF나 모든 페이지 이미지를 바로 보내지 않습니다.

1. PyMuPDF 등으로 텍스트와 페이지 구조를 로컬 추출합니다.
2. 로컬 표 파서로 읽을 수 있는 표를 먼저 구조화합니다.
3. 텍스트가 없는 페이지에만 OCR을 적용합니다.
4. 규칙으로 확정 가능한 값은 로컬 검증합니다.
5. 모호한 후보행과 짧은 원문 근거만 LLM에 전달합니다.

동일 파일·페이지·프롬프트 조합의 성공 결과를 캐시하고 실패 재시도 횟수를
제한합니다. 성공한 페이지를 다시 보내지 않습니다.

### 8.2 모델 선택과 비용 정책

- 제공자: OpenAI API
- API 키: 사용자가 실제 시험 직전에 로컬 `.env`에 입력
- 모델: 사전 고정하지 않고 대표 문서 파일럿 후 선택
- 2개월 전체 예산: 100달러
- 제작·QA 목표 상한: 80달러
- 시연·복구 예비비: 최소 20달러

API 호출 전 다음 순서로 견적을 확정합니다.

1. 전체 PDF 페이지와 로컬 추출 가능 페이지를 집계합니다.
2. LLM이 필요한 후보 페이지·행만 계산합니다.
3. 대표 문서로 후보 모델별 실제 입력·출력 토큰과 비용을 측정합니다.
4. 구조화 성공률, 수기 수정량, 처리시간과 비용을 함께 비교합니다.
5. 합격 품질을 만족하는 가장 저렴한 모델과 호출전략을 선택합니다.
6. 전체 문서 예상비용과 상·하한을 사용자에게 보고하고 승인받습니다.

호출별 모델, 파일·페이지, 입력·출력 토큰, 캐시 토큰, 예상·실제 비용과
오류를 기록합니다. 실행별 비용 상한을 넘기기 전에 중단하며 사용자의 추가
승인 없이 80달러 목표 상한을 해제하지 않습니다.

### 8.3 선택 부착과 실패 격리

```text
PDF
→ 로컬 추출·OCR·표 파싱
→ LLM 구조화 후보
→ 별도 임시 저장
→ 자동 검증
→ 사람 검수
→ 승인된 데이터만 승격
→ 기존 분석 파이프라인
```

수기 기준선은 덮어쓰지 않습니다. LLM 결과가 필수 스키마·기본키·숫자·단위·
원문 페이지·수기 대조 검증을 통과하지 못하면 승격하지 않습니다. 따라서
실패 시 코드를 되돌리거나 대시보드에서 떼어낼 필요 없이 수기 기준선을
계속 사용합니다.

8월 25일 시연에서는 전체 문서를 현장에서 처음 처리하는 방식에 의존하지
않습니다. 검증된 캐시 결과를 기본으로 보여주고, 라이브 실행이 필요하면
짧은 대표 구간만 별도로 실행합니다.

## 9. 순위와 가중치 운영

- 검증된 복수 시나리오를 기본 선택지로 제공합니다.
- 한 가중치 결과를 정답으로 고정하지 않습니다.
- 전체 순위와 부처 내부 순위를 모두 제공합니다.
- 순위범위, 시나리오 합의도와 데이터 신뢰도를 함께 표시합니다.
- 전문가용 자유 가중치 조정은 고급 기능으로 분리합니다.
- 자유 가중치 결과를 프로젝트의 공식 결론으로 자동 저장하지 않습니다.
- 결측값을 0점 처리하거나 남은 변수에 가중치를 자동 재배분하지 않습니다.

## 10. 2026-08-03 수기 기준선과 2026-08-05 선택형 LLM

반드시 완료합니다.

1. 설정 기반 N개 부처 처리 구조
2. 현재 4개 부처 성과·재정 통합 마스터
3. 전체·부처별 복수 시나리오와 순위 안정성
4. 프로그램 맥락 아래 세부사업 최종 검토대기열
5. 데이터 품질과 원문검수 상태 분리
6. 4개 부처를 모두 탐색할 수 있는 대시보드
7. 상위 후보 사례와 분석적 발견
8. 실행·품질검증·해석한계 기록

2026-08-03에는 위 결과를 `manual-v1` 기준선으로 동결합니다. 같은 날 최신
성과계획서를 별도 입력으로 처리해 어느 세부사업부터 증액·감액 필요성을
검토할지 그림자 실행합니다. 구체적인 조정액은 산정하지 않습니다.

8월 4~5일에는 LLM 모듈을 별도 경로에서 제작·검증합니다. 8월 5일
Go/No-Go 시점까지 필수 검증을 통과하면 선택형 입력으로 연결하고, 실패하면
`manual-v1`을 최종본으로 유지합니다.

2026-08-05 이후로 미룹니다.

- 행정안전부 데이터 복구·추가
- 전체 중앙부처 실제 데이터 수집
- 자동 증액·감액·폐지 판단
- 운영환경 수준의 사용자·권한·승인 워크플로

## 11. 경진대회 성공조건

시스템 기능의 수가 아니라 다음을 성공으로 봅니다.

- 현재 4개 부처에서 재현 가능한 점검 우선순위가 생성됨
- 왜 해당 후보를 먼저 봐야 하는지 구성요소와 원문근거로 설명 가능함
- 전체 순위와 부처별 순위의 용도가 분리됨
- 가중치가 바뀌어도 반복되는 후보와 민감한 후보가 구분됨
- 데이터 오류 후보가 사업 문제 후보와 분리됨
- 프로그램 성과와 세부사업 재정근거의 계층이 보존됨
- 실제 상위 사례에서 재정·성과관리 시사점을 설명할 수 있음
- 새 부처는 데이터와 설정만 추가하여 같은 절차로 처리할 수 있음

정책적 발견이 강하지 않더라도, 어떤 규칙과 근거로 검토순서를 정했고 결과가
시나리오 변화에 얼마나 안정적인지를 명확히 설명하면 유효한 결과입니다.

경진대회 MVP의 필수 결과는 현재 확보한 4개 부처 수기 성과데이터로 만든
재현 가능한 점검 우선순위와 대시보드입니다. 최신 성과계획서 투입은 별도
그림자 실행으로 검증합니다.

LLM 모듈은 8월 5일까지 성공하면 선택형 기능으로 붙이고, 실패하거나 비용·
품질 기준을 넘지 못하면 후속 고도화 설계와 파일럿 결과만 발표합니다.
LLM의 부착 여부는 핵심 프로젝트의 완료 여부를 바꾸지 않습니다.
