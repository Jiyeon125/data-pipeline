# 점검 우선순위 트리아지·분류모델 구현 계획

작성일: 2026-08-01  
상태: **구현 대기** — PDF→데이터셋 LLM 파이프라인이 안정화된 뒤 착수합니다.

## 1. 한 문장 목표

재정·성과관리 실무자가 긴 원문을 먼저 읽지 않고도 **어떤 세부사업의 어떤 근거부터
확인해야 하는지** 알 수 있는 점검 업무대기열을 만듭니다.

이 시스템은 실패·낭비·감액·폐지를 자동 판정하지 않습니다.

## 2. 최종 흐름

```text
PDF 파싱
→ 성과·재정 마스터 결합
→ 파생변수 생성
→ 비교 가능한 사업끼리 상대비교
→ 네 가지 독립 점검신호 생성
→ 반복·복수 신호 중심의 업무단계 분류
→ 전체·부처별 점검순서 산출
→ 공식 평가결과 분류모델을 보조열로 연결
→ LLM이 이유·반대근거·확인사항 설명
→ 전문가 최종 판단
```

## 3. PDF 파싱 파이프라인과의 경계

### 파싱 파이프라인의 역할

문서에 존재하는 사실과 근거만 반환합니다.

- 부처, 연도, 프로그램명·코드
- 성과지표명, 단위, 방향
- 계획목표, 보고목표, 실적, 공식 달성률
- 목표변경 전·후 값과 변경 사유
- 성과지표 유형 후보
- 기대 성과시차 후보
- 사업 전달방식·재정수단 후보
- 출처 파일, 원문 페이지, 근거문장
- 추출·대조·사람검수 상태

### 우선순위 엔진의 역할

- 파싱값과 예산·집행·결산을 연결합니다.
- 산식과 동료집단을 적용합니다.
- 독립 신호와 업무순서를 만듭니다.
- 데이터가 없거나 불확실한 값을 0점으로 만들지 않습니다.

### LLM이 하지 않는 일

- 최종 순위 직접 결정
- 사업 필요성·감액 필요성 임의 판정
- 누락된 수치 추정
- 분류모델 결과 변경
- 프로그램 성과를 세부사업 성과로 귀속

## 4. 분석 단위

### 신호 생성 단위

```text
부처 × 프로그램 × 회계연도 × 회계유형
```

성과지표는 프로그램 단위이므로 이 수준에서 성과 맥락을 만듭니다.

### 최종 점검행

```text
부처 × 프로그램 × 세부사업 × 회계연도 × 회계유형
```

세부사업에는 자기 예산·집행·구조 신호만 붙입니다. 프로그램 성과는
`상위 프로그램 성과 맥락` 열로만 표시합니다.

### 월별 집행 단위

```text
부처 × 회계연도 × 집행연월 × 회계 × 프로그램 × 단위사업 × 세부사업
```

## 5. 네 가지 독립 점검신호

네 신호는 0~100의 `동료집단 점검강도 백분위`로 표현할 수 있지만 기본 화면에서
합산하지 않습니다.

| 신호 | 실무 질문 | 핵심 파생변수 | 기본 해석 |
|---|---|---|---|
| 성과 | 목표달성이 일부·전반·반복 중 무엇인가 | 미달비율, 중앙부족, 최악부족, 반복 미달 | 성과 설명 또는 지표 재설계 검토 |
| 집행 | 같은 성격 사업보다 집행이 취약한가 | 집행률, 동료집단 하위꼬리, 반복 저집행, 연말집중 | 집행사유 확인 |
| 성과–예산 불일치 | 성과와 후속예산 방향이 어긋나는가 | 성과미달×실질증액, T+1·T+2 방향 | 예산환류 설명 필요 |
| 예산구조 | 프로그램 내부 배분이 크게 달라졌는가 | top1·top3, 정규화 HHI, HHI 변화, 재배분 거리 | 구조변경·집중 원인 확인 |

### 5.1 성과 신호

지표 `j`의 공식 달성률을 `r_j`라고 합니다.

```text
indicator_coverage = 유효 달성률 지표 수 / 전체 지표 수
under_target_share = count(r_j < 100) / count(valid r_j)
median_shortfall = median(max(0, 1 - r_j / 100))
worst_shortfall = max(max(0, 1 - r_j / 100))
repeated_under_rate = 미달 관측연도 수 / 유효 관측연도 수
```

평균 달성률 하나는 사용하지 않습니다. 과도달성이 미달을 상쇄할 수 있기 때문입니다.

### 5.2 집행 신호

분모가 확인된 집행률만 사용합니다.

```text
execution_gap = max(0, 1 - execution_rate)
peer_execution_tail = 1 - ECDF_peer(execution_rate)
repeated_low_rate = 저집행 연도 수 / 유효 집행연도 수
q4_share = (12월 누계 - 9월 누계) / 12월 누계
december_share = (12월 누계 - 11월 누계) / 12월 누계
```

80%·90% 같은 절대기준과 동료집단 하위 10%·20%를 함께 보여줍니다. 집행률 100%
초과는 위험점수가 아니라 분모·조인·회계조정 검증으로 보냅니다.

### 5.3 성과–예산 불일치 신호

동일 금액유형을 GDP 디플레이터로 실질화합니다.

```text
real_budget_t = nominal_budget_t / deflator_t
real_growth_h = real_budget_(t+h) / real_budget_t - 1
underperformance_increase_h = performance_shortfall × max(real_growth_h, 0)
```

T+1과 T+2를 합치지 않습니다. 성과 양호+예산 감소는 대칭적인 문제점수가 아니라
구조변경 맥락으로 따로 표시합니다.

### 5.4 예산구조 신호

세부사업 예산비중을 `s_k`라고 합니다.

```text
HHI = sum(s_k²)
normalized_HHI = (HHI - 1/n) / (1 - 1/n), n >= 2
reallocation_distance = 0.5 × sum(|s_(k,t+1) - s_(k,t)|)
```

세부사업이 하나인 프로그램은 `단일 구성`이지 자동 고위험이 아닙니다. 코드변경·통합·
분할 후보는 연결을 확인한 뒤 변화량을 계산합니다.

## 6. 동료집단

기본 동료집단은 다음과 같습니다.

```text
회계연도 × 회계유형 × 검증된 재정수단 × 기대 성과시차
```

필요하면 전달방식을 추가합니다.

- 즉시 서비스
- 연간 보조·출연
- 하위기관 집행
- 다년 R&D
- 다년 시설
- 융자·보증 등 금융지원
- 미분류

표본이 작으면 부처를 먼저 제거해 비교집단을 넓힙니다. 그래도 작으면 상대백분위를
만들지 않고 절대기준과 `소표본` 경고만 표시합니다. 최소 표본 수는 실제 분포와
민감도 검증 후 확정합니다.

## 7. 두 개의 업무대기열

### 7.1 데이터 검증 대기열

정책 우선순위와 분리합니다.

- 금액 단위·금액유형 미확정
- 집행률 분모 미확정
- 프로그램 PARTIAL·UNMATCHED
- 성과 원문·산식 차단 오류
- 키 충돌·중복·관측연결 문제

표시값은 `DATA_FIRST`입니다. 정책적으로 나쁘다는 뜻이 아닙니다.

### 7.2 정책 점검 대기열

```text
REPEATED_OR_MULTIPLE  반복 신호 또는 독립 신호가 여러 개
STRONG_SINGLE         매우 강한 단일 신호
SINGLE_REVIEW         보통 단일 신호
CONTEXT_REVIEW        구조변경·성과양호+감액 등 맥락 확인
MONITOR               현재 관측에서 우선 신호 없음
```

`MONITOR`를 `안전`으로 표현하지 않습니다.

## 8. 전체·부처별 점검순서

가중합 대신 다음 사전식 정렬키를 사용합니다.

```text
1. 업무대기열 단계
2. 반복 신호 유형 수 내림차순
3. 독립 신호 유형 수 내림차순
4. 가장 강한 유형의 동료집단 백분위 내림차순
5. 근거 신뢰도
6. 실질 예산 영향규모 내림차순
7. 안정적인 후보 ID
```

예산규모는 위험이 아니라 같은 수준 후보의 검토 파급효과입니다.

- 전체 순서: 비교 가능한 전체 동료집단에서 계산
- 부처별 순서: 같은 규칙을 적용하되 부처 내부 영향규모·업무순서 계산

## 10. 사용자에게 보여줄 설명 형식

### 예측 이유

> 같은 유형 사업 중 집행률이 하위 12%이고 저집행이 2년 반복됐습니다. 상위
> 프로그램은 성과지표 3개 중 2개가 목표에 미달했지만 다음 연도 실질예산은 14%
> 증가했습니다. 독립 신호 3개가 함께 나타나 우선 검토 단계로 분류했습니다.

### 반대 근거

> 다년 R&D 사업으로 성과가 늦게 나타날 가능성이 있으므로 사업일정과 기대
> 성과시차를 확인해야 합니다.

### 다음 행동

> 저집행 사유, 목표변경 근거, 다음 연도 증액 사유를 원문에서 확인합니다.

설명은 다음 네 질문에 답해야 합니다.

1. 왜 지금 봐야 하는가
2. 무엇과 비교했는가
3. 어떤 반대해석이 가능한가
4. 실무자가 다음에 무엇을 확인해야 하는가

## 11. 공식 평가결과 Classification 모델

기본 업무대기열을 먼저 완성한 뒤 보조 신호로 추가합니다.

### 첫 파일럿 타깃

```text
y_cut = 1  if official_result == "감액"
y_cut = 0  if official_result in {"정상추진", "사업개선"}
```

현재 확인된 2026년 4개 부처 공개결과는 524행이고, 2024 세부사업과
`부처×사업명×회계`로 정확히 연결된 400행 중 감액 이진 파일럿 적격은 397행입니다.

```text
감액 171 : 비감액 226
```

5분류는 정상추진·통합·폐지 표본이 너무 적어 현재 사용하지 않습니다. 사업 필요성
상·중·하는 최종 감액결과와 다른 타깃이므로 문항별 전문가 라벨이 확보된 뒤 별도
모델로 만듭니다.

### 첫 모형

- 표준화 수치변수 + 원-핫 범주변수 로지스틱 회귀
- 부처코드·사업명·고유 ID는 기본 입력에서 제외
- 평가시점 이후 예산과 공식 결과를 암시하는 문구 제외
- 프로그램 성과는 세부사업의 상위 맥락 변수로만 사용

현재 환경에는 `scikit-learn`이 없습니다. 모델 구현 착수 시 명시적 의존성으로 추가하고
자체 최적화 코드는 만들지 않습니다.

### 검증

- leave-one-ministry-out
- 프로그램 그룹 분할
- 향후 과거연도 학습→미래연도 검증
- balanced accuracy, macro F1, 감액 PR-AUC
- Brier score와 확률 보정
- precision@K·recall@K
- 부처·회계·규모별 성능

전체 정확도 하나만으로 채택하지 않습니다.

### 상·중·하 표시

분류모델은 먼저 보정된 확률을 냅니다.

```text
P(공식 감액결과 | 평가 이전 파생변수)
```

상·중·하 경계는 0.5 같은 임의값이 아니라 전문가 검토 가능 건수와 감액 누락비용을
기준으로 precision-recall 곡선에서 정합니다. 이 값의 이름은 `사업 필요성`이 아니라
`공식 감액결과 예측 가능성`입니다.

## 12. LLM 설명 계약

LLM은 모델 출력과 근거만 받아 자연어로 설명합니다.

```json
{
  "predicted_class": "CUT_REVIEW_HIGH",
  "calibrated_probability": 0.73,
  "positive_contributors": [],
  "negative_contributors": [],
  "raw_feature_values": {},
  "peer_percentiles": {},
  "source_evidence": [],
  "model_version": "...",
  "feature_cutoff_date": "..."
}
```

허용 출력:

- 예측 이유
- 예측을 낮추는 반대 근거
- 추가 확인사항
- 근거 부족 여부

금지 출력:

- 모델 등급 변경
- 제공되지 않은 숫자·사실 생성
- 감액·폐지 확정 표현
- 근거 없는 인과관계

가능하면 먼저 규칙형 문장 템플릿으로 설명을 만들고, LLM은 문장 다듬기와 원문 근거
요약에만 사용합니다.

## 13. 구현 순서

### 단계 0. 착수 조건

- PDF 파싱 출력 스키마가 동결됐습니다.
- 4개 부처 입력에서 필수 필드 누락·근거상태가 집계됩니다.
- 파싱 재실행 시 행과 키가 안정적으로 재현됩니다.

### 단계 1. 성과 파생변수

- 지표 사용가능률
- 미달비율
- 중앙·최악 달성부족
- 반복 미달
- 목표변경·산식검토 가드레일

### 단계 2. 집행·동료집단

- 올바른 회계별 분모
- 절대 기준과 ECDF
- 반복 저집행
- 4분기·12월 집중

### 단계 3. 환류·구조

- T+1·T+2 실질 예산증감
- 비대칭 불일치
- 정규화 HHI·변화
- 재배분 거리

### 단계 4. 독립 신호 마스터·대기열

- 데이터 검증·정책 점검 분리
- 전체·부처별 순서
- 유형별 큐
- 설명에 필요한 원값·백분위·근거 연결

### 단계 5. 사례 검증·대시보드

- 상위 후보와 반례 원문 확인
- 업무대기열·사업상세·동료비교·원문 이동
- `안전` 대신 `현재 관측에서 우선 신호 없음` 사용

### 단계 6. Classification 파일럿

- 공식 결과·특징 시점 정렬
- 로지스틱 회귀 기준선
- 부처 단위 외부검증
- 보정확률과 설명 기여도 생성
- 검증 전 기본 우선순위에 합산하지 않음

### 단계 7. LLM 설명 연결

- 모델·규칙 결과를 잠금 입력으로 전달
- 이유·반대근거·확인사항 생성
- 근거문장·페이지 연결
- 사람 확인 결과 별도 보존

## 14. 완료 기준

- 전체 후보가 데이터·정책·모니터 중 하나의 상태를 갖습니다.
- 결측을 0점으로 대체하지 않습니다.
- 회계유형과 T+1·T+2를 섞지 않습니다.
- 프로그램 전체금액과 분석부분합계를 분리합니다.
- 프로그램 성과의 세부사업 귀속은 0건입니다.
- 전체·부처별 업무순서가 동일한 규칙으로 재현됩니다.
- 각 후보에서 원값·동료집단·근거·다음 행동을 확인할 수 있습니다.
- 상위 후보와 반례의 원문 검토 결과가 기록됩니다.
- 분류모델은 무작위 정확도가 아니라 부처 외부검증과 보정도를 통과합니다.
- LLM 설명의 숫자·근거가 입력과 모두 일치합니다.
- 산출물·테스트·의사결정 근거가 `docs/WORK_LOG.md`에 기록됩니다.

## 15. 채택하지 않는 방식

- 성과·집행·환류·구조를 임의 가중합한 단일 위험점수
- 결측값 0점 처리와 남은 변수 가중치 자동 재배분
- 예산규모가 크다는 이유만으로 위험도 상승
- 기금·융자·일반회계 직접 비교
- 성과 양호+예산 감소와 성과 미달+예산 증가의 대칭 처리
- 공식 감액결과를 사업 필요성의 정답으로 사용
- 분류모델 검증 전 기본 업무순서에 확률 합산
- LLM이 예측결과나 정책결론을 생성
