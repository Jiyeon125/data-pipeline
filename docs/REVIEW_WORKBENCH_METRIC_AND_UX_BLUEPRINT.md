# 재정사업 점검 작업대 지표·사용자경험 개편 기획안

> 구현 상태(2026-07-31): 이 기획의 비가중 점검강도, 3,301행 통합
> 점검대기열, 4화면 Streamlit 흐름을 구현했습니다. 사업별 기대시차,
> 의무지출, 목·비목, 융자 순재정부담은 원자료 부재로 후속 범위입니다.

## 1. 권장 결정

기본 대시보드에서 네 구성요소 가중합과 평균 시나리오 순위를 제거한다.

대신 다음 구조를 사용한다.

```text
사업성격과 데이터상태 확인
→ 성과·집행·환류·예산구조 신호를 독립적으로 표시
→ 반복성과 복수 신호로 점검강도 분류
→ 본예산 규모는 같은 점검강도 안의 업무순서 보조값으로만 사용
→ 프로그램 맥락 아래 세부사업 자체 재정근거를 확인
→ 원문과 사람 판단으로 검토결과 기록
```

가중치 시나리오는 삭제하지 않고 `고급 민감도 분석`으로 이동한다. 이는 과거
결과의 재현성과 발표 참고자료를 보존하기 위한 것이며 기본 업무순서에는
사용하지 않는다.

## 2. 사용자가 내릴 결정

### 주 사용자

- 재정·성과관리 실무자
- 성과계획서 제출과 예산안 확정 사이에 검토하는 담당자

### 단 하나의 의사결정

> 제한된 시간 안에서 어떤 세부사업의 어떤 근거부터 확인할 것인가?

대시보드는 다음을 결정하도록 돕는다.

1. 데이터부터 고쳐야 하는가
2. 성과 원문을 확인해야 하는가
3. 집행지연 사유를 확인해야 하는가
4. T+1·T+2 예산변화 근거를 확인해야 하는가
5. 프로그램 내부 예산구조를 확인해야 하는가
6. 현재 신호는 없지만 모니터링할 것인가

대시보드는 삭감·증액·폐지·실패를 결정하지 않는다.

## 3. 사용자 업무 흐름

```text
업무현황
→ 점검대기열
→ 사업 상세
→ 비교·원문 근거
→ 검토결과 기록
```

사용자가 처음부터 그래프와 복잡한 점수를 해석하게 하지 않는다. 첫 화면에서
오늘 확인할 업무량과 다음 행동을 보여주고, 상세 근거는 선택한 사업에서
단계적으로 연다.

## 4. 가중합을 대체할 점검강도

점검강도는 점수구간이 아니라 설명 가능한 규칙으로 정한다.

### 4.1 점검강도

| 순서 | 점검강도 | 진입 조건 | 사용자에게 보이는 다음 행동 |
|---:|---|---|---|
| 1 | `DATA_FIRST` | 연결·분모·금액·원문 핵심값 검증 필요 | 데이터 근거 확인 |
| 2 | `REPEATED_OR_MULTIPLE` | 반복 강한 신호 또는 서로 다른 신호군 2개 이상 | 성과·집행·예산 근거 종합 확인 |
| 3 | `STRONG_SINGLE` | 현재연도 강한 단일 신호 | 해당 신호 원인 확인 |
| 4 | `SINGLE_REVIEW` | 독립 신호 1개 | 신호별 원문·추세 확인 |
| 5 | `CONTEXT_REVIEW` | 회계·구조·사업계보 맥락만 존재 | 구조변경·회계 맥락 확인 |
| 6 | `MONITOR` | 현재 정의된 신호 미검출 | 안전판정 없이 모니터링 |

### 4.2 같은 점검강도 안의 순서

가중합하지 않고 다음 키를 차례로 적용한다.

```text
1. 반복 발생 여부와 반복 횟수 내림차순
2. 서로 다른 독립 신호군 수 내림차순
3. 원문·금액·분모 근거의 확인상태
4. 본예산 규모 내림차순
5. 안정적인 사업 식별자
```

본예산 규모는 문제의 심각도가 아니라 같은 조건에서 검토 파급효과가 큰
사업을 먼저 보기 위한 동순위 보조값이다.

### 4.3 현재 데이터에 적용 가능한 기준선

현재 412개 프로그램-연도-회계유형 후보의 기존 비가중 유형은 다음과 같다.

| 현재 유형 | 행 | 본예산 비중 | 개편안 대응 |
|---|---:|---:|---|
| 데이터 검증 | 15 | 8.30% | `DATA_FIRST` |
| 복수 신호 | 80 | 17.62% | `REPEATED_OR_MULTIPLE` |
| 강한 단일 신호 | 24 | 13.08% | `STRONG_SINGLE` |
| 일반 신호 | 131 | 34.82% | `SINGLE_REVIEW`, 반복성으로 일부 상향 |
| 맥락 검토 | 37 | 7.33% | `CONTEXT_REVIEW` |
| 정보·신호 미검출 | 125 | 18.86% | `MONITOR` |

이 값은 최종 개편 후 확정 수치가 아니라, 가중합 없이도 전체 업무를
분류할 수 있음을 확인하는 기준선이다.

## 5. 지표 모델

## 5.1 점수에 넣지 않는 맥락

다음 값은 필터·비교집단·경고에 사용한다.

| 맥락 | 사용 방식 |
|---|---|
| 부처·연도 | 전체와 부처 내부 업무량 분리 |
| 회계유형 | 일반·특별·기금 분모와 잔액구조 분리 |
| 재정수단 | 같은 수단끼리만 상대 비교 |
| 사업 전달방식 | 즉시 서비스·하위기관 집행·다년도 R&D·시설·정책금융 구분 |
| 기대 성과시차 | T·T+1·T+2·장기·미확인 구분 |
| 의무지출·조정가능성 | 재량사업과 별도 해석 |
| 사업 생애주기 | 신규·종료·이관·통합·분할·단계전환 구분 |
| 사업규모 | 규모구간 층화와 동순위 정렬 |
| 데이터상태 | 정책검토보다 데이터검증이 먼저인지 판단 |

재정수단·사업유형이 수기 확정되지 않은 행에는 상대순위를 기본 판단으로
사용하지 않는다. 후보 분류는 화면에 `미확정` 배지를 표시한다.

## 5.2 성과 신호

기본 화면에 모두 노출하지 않고 대표값과 경고만 표시한다.

### 대표 표시

- 미달지표 수 / 비교가능 지표 수
- 미달지표 비율
- 최저 달성률
- 반복미달 횟수
- 목표치 변경 여부
- 성과지표 유형 구성

### 상세 표시

- 지표별 목표·실적·공식 달성률
- 중앙값 달성률
- INPUT·PROCESS·OUTPUT·OUTCOME 비율
- 과대달성 지표
- 산식·방향 검토 필요
- 원문 검수상태

### 강한 신호 후보

- 비교가능 지표 전부 미달
- 동일 프로그램의 2개 이상 연도 반복미달
- 목표치 하향 변경 후 표면적 달성

목표치 변경과 지표유형은 원문 확인 전 자동 확정하지 않는다.

## 5.3 집행 신호

### 대표 표시

- 현재 집행률과 분모 상태
- `<80%`, `80~90%`, `90% 이상`
- 반복 저집행 횟수 / 유효관측연도
- 4분기·12월 집행집중
- 이월·불용
- 집행지연 사유 검수상태

### 기본 규칙

- 집행률 80% 미만: 강한 현재 신호 후보
- 집행률 80~90%: 주의 신호
- 2회 이상이면서 유효연도의 50% 이상: 반복 신호
- 4분기 40% 이상 또는 12월 20% 이상: 연말집중 설명 필요

상대 하위 10%·20%는 비교집단이 검증되고 표본이 충분할 때만 보조로 쓴다.
낮은 집행률은 실패가 아니라 집행사유 확인 신호다.

## 5.4 예산 환류 신호

동년도, T+1, T+2를 별도 열과 타임라인으로 표시한다.

### 대표 표시

- T년도 성과·집행
- T+1 명목·실질 예산변화
- T+2 명목·실질 예산변화
- 프로그램 내부 세부사업 재배분
- 공식 예산변화 사유 검수상태

### 비대칭 유형

| 유형 | 표시 | 사용 |
|---|---|---|
| 성과 미달 + 실질예산 증가 | `성과·예산 확인 필요` | 우선 원문 검토 |
| 성과 양호 + 예산 감소 | `구조변경 가능성` | 위험점수 없이 맥락 확인 |
| 집행 설명 필요 + 예산 증가 | `집행계획·증액근거 확인` | 집행사유와 증액근거 확인 |
| 집행 설명 필요 + 예산 감소 | `사업축소·종료 여부 확인` | 생애주기와 공식사유 확인 |

T+1과 T+2 중 하나를 미리 정답으로 고르지 않는다. 두 값을 함께 보여주고
사업의 기대 성과시차와 연결한다.

## 5.5 예산구조 신호

### 현재 데이터로 가능한 값

- 세부사업 수
- Top1·Top3 예산비중
- HHI·세부사업 수 보정 HHI
- 프로그램 총예산과 분석대상 예산비중
- 세부사업별 예산증감
- 프로그램 내부 재배분
- 단일 세부사업 프로그램 여부

### 해석 규칙

- 세부사업 1개는 집중도 100%를 문제로 표시하지 않는다.
- 세부사업 2개는 별도 소집단으로 표시한다.
- 세부사업 3개 이상에서 집중도와 변화량을 비교한다.
- 집중도가 높다는 사실보다 전년 대비 급변과 어떤 세부사업이 변화를
  만들었는지를 보여준다.

목·비목 구성, 사업목적 외 지출, 융자금 외 부대비용 비중은 추가 원자료가
생기기 전까지 `미구현`으로 표시한다.

## 5.6 데이터·근거 가드레일

다음 값은 별도 열과 배지로 유지한다.

- 성과·재정 매칭상태
- 금액유형과 단위 확인
- 집행률 분모 확인
- 원문 페이지 존재
- 사람 검수상태
- 구조적 결측사유
- 사업계보 검수상태
- 사업성격·기대시차 검수상태

데이터 신뢰도가 낮으면 정책신호를 낮은 점수로 만들지 않고
`DATA_FIRST`로 이동한다.

## 6. 사업성격과 시차 입력

성과 발현 시차는 프로그램 성과의 맥락이므로 우선 프로그램 수준에서 관리한다.
세부사업별 전달방식은 재정수단과 사업내용을 별도로 표시한다.

권장 최소 스키마:

```text
ministry_code
program_code
delivery_pattern
expected_outcome_lag
mandatory_expenditure_status
classification_evidence
evidence_page
review_status
reviewer
review_note
```

허용 후보:

```text
delivery_pattern:
  IMMEDIATE_SERVICE
  ANNUAL_TRANSFER
  DOWNSTREAM_EXECUTION
  MULTIYEAR_RND
  MULTIYEAR_INFRASTRUCTURE
  FINANCIAL_SUPPORT
  UNKNOWN

expected_outcome_lag:
  T
  T_PLUS_1
  T_PLUS_2
  LONGER
  UNKNOWN
```

전체 79개 프로그램을 처음부터 수기 검수하지 않는다. 1차 독립 신호로
우선 후보를 좁힌 뒤 발표 사례와 상위 검토 프로그램부터 근거를 확인한다.

## 7. 화면 설계

## 7.1 화면 1 — 업무현황

사용자 질문:

> 오늘 무엇을 얼마나 확인해야 하는가?

상단 카드:

- 우선 확인 업무
- 반복 또는 복수 신호
- 데이터 먼저 확인
- 원문 검수 미완료
- 현재 필터의 본예산 범위

본문:

- 점검강도별 행 수와 본예산 비중
- 부처별 업무량
- 반복 신호와 단년도 신호 분포
- 데이터 미확정이 많은 부처·회계
- 새로 발견된 주요 패턴 2~3개

Top 5와 단일 평균순위는 첫 화면에서 제거한다.

## 7.2 화면 2 — 점검대기열

사용자 질문:

> 어느 사업부터 무엇을 확인해야 하는가?

필수 열:

```text
업무순서
다음 행동
부처
세부사업
상위 프로그램
연도
회계유형
사업성격
기대시차
성과 신호
집행 신호
T+1 환류
T+2 환류
예산구조
반복성
본예산
근거상태
```

기본 정렬은 점검강도와 사전 정의된 순차 정렬키를 사용한다.
사용자는 열 정렬로 자신의 업무관점에 맞게 다시 볼 수 있다.

필터는 다음 여섯 개를 기본으로 제한한다.

- 부처
- 연도
- 점검강도
- 신호유형
- 회계유형
- 데이터·원문 상태

사업성격과 기대시차는 검수된 값이 늘면 고급 필터로 추가한다.

행을 선택하면 같은 페이지 아래 또는 사업 상세 화면으로 이동한다.

## 7.3 화면 3 — 사업 상세

사용자 질문:

> 왜 이 사업이 올라왔고, 어떤 근거를 확인해야 하는가?

상단:

- 다음 행동 한 문장
- 점검강도
- 신호 배지
- 근거상태
- 본예산

본문 순서:

1. `왜 올라왔는가`: 독립 신호 카드
2. `시간 흐름`: T-1·T·T+1·T+2 성과·집행·예산 타임라인
3. `프로그램 성과 맥락`: 지표별 목표·실적·달성률·반복성
4. `세부사업 재정원인`: 예산·집행·이월·불용·집중도
5. `사업성격`: 전달방식·기대시차·의무지출·생애주기
6. `근거 검수`: PDF 페이지·공식자료·검토 메모

프로그램 성과는 `상위 프로그램 맥락`으로 표시하고 세부사업 성과로
귀속하지 않는다.

## 7.4 화면 4 — 비교와 근거 검수

사용자 질문:

> 이 값이 같은 성격의 사업 안에서도 특이한가?

- 검증된 비교집단이 있을 때만 분포와 선택 사업의 위치를 표시
- 비교집단 크기와 검수상태를 항상 표시
- 소표본이면 순위를 숨기고 원값만 표시
- 원문 페이지와 수기값을 나란히 표시
- 검토상태·검토자·메모를 저장

기존 `순위 안정성` 화면은 기본 흐름에서 제거하고
`고급 분석 > 가중치 민감도`로 이동한다.

## 8. 최종 검토대기열의 한 행

정상 분석행:

```text
부처 × 프로그램 × 세부사업 × 회계연도 × 회계유형
```

데이터 차단행:

```text
PROGRAM_DATA_TASK
```

재정 연결 전에 세부사업을 억지로 만들지 않는다. 따라서 대기열은 다음 두
업무유형을 허용한다.

```text
review_item_type:
  DETAILED_PROJECT_REVIEW
  PROGRAM_DATA_TASK
```

정상 분석행 397개 프로그램 후보는 현재 3,286개 세부사업-연도 행으로
연결 가능하다. 데이터 검증 15행은 프로그램 데이터 작업으로 유지한다.

## 9. 실무자에게 제공할 인사이트

대시보드는 단순 상위 사업 목록보다 다음 질문에 답해야 한다.

1. 반복 저집행은 어떤 사업 전달방식에서 집중되는가
2. 다년도 R&D·시설사업을 제외해도 반복 신호가 남는가
3. 성과미달 뒤 예산 증가는 T+1과 T+2 중 언제 더 자주 나타나는가
4. 성과양호·예산감소 사례 중 정상 종료·단계전환은 무엇인가
5. 프로그램 내부에서 어떤 세부사업이 예산·집행 변화를 주도하는가
6. 회계유형과 재정수단을 분리하면 기존 신호가 유지되는가
7. 데이터 미확정 때문에 판단이 막히는 예산 규모는 얼마인가
8. 원문 확인 후 신호가 해소되거나 강화된 사례는 무엇인가

이 질문의 결과가 발표의 분석적 발견이 된다. 대시보드는 그 결과를 탐색하고
근거를 확인하는 수단이다.

## 10. 구현 범위

## 10.1 제출 전 MVP

1. 가중합·평균순위를 기본 업무순서에서 제거
2. 독립 신호 마스터와 점검강도 생성
3. T·T+1·T+2를 별도 열로 연결
4. 프로그램 맥락→세부사업 자체 재정근거의 2단계 순서 유지
5. 업무현황·점검대기열·사업상세·원문검수 화면 개편
6. 현재 4개 부처 전체와 부처별 필터 제공
7. 상위 사례와 반례 원문 검수

## 10.2 제출 후 고도화

- 전체 프로그램 사업성격·기대시차 검수
- 의무지출·법적 조정가능성 연결
- 목·비목 예산구조
- 융자 공급·회수·순재정부담
- 외부 평가자료와 개선계획
- 전문가 선택형 가중치 분석
- LLM 구조화 모듈 연결

## 11. 구현 순서

### 1단계 — 분석 계약

- 지표 사전 확정
- 점검강도 규칙 확정
- 비교집단 적격성 확정
- 현재 가중합 산출물은 `legacy sensitivity`로 표시

### 2단계 — 분석 마스터

- 412행 독립 신호표 생성
- T+1·T+2 연결
- 15개 데이터 작업과 3,286개 세부사업 검토행 결합
- 입출력 행·금액·키·결측 검증

### 3단계 — 대시보드

- 기존 다섯 단계를 네 화면으로 단순화
- 기본 업무대기열과 행 선택 상세 연결
- 원문 검수와 검토상태 저장 재사용
- 별도 의존성이나 커스텀 컴포넌트 추가 없음

### 4단계 — QA와 사례

- 부처·회계별 편향
- 점검강도별 행·금액 비중
- 신호 제거 민감도
- 상위 사례·반례 원문 검수
- Streamlit AppTest
- 발표용 발견과 한계 정리

## 12. 완료 수용기준

- 412개 프로그램-회계유형-연도 업무가 누락되지 않는다.
- 데이터 검증 15행을 세부사업 성과행으로 억지 변환하지 않는다.
- 정상 397개 후보의 세부사업 연결과 금액합계가 보존된다.
- 가중합·평균순위가 기본 업무순서에 사용되지 않는다.
- T·T+1·T+2가 별도 필드와 별도 설명으로 유지된다.
- 성과양호·예산감소가 위험점수로 처리되지 않는다.
- 재정수단·사업유형 미확정 행의 상대순위를 기본 판단에 사용하지 않는다.
- 프로그램 성과를 세부사업 성과로 귀속한 행이 0개다.
- 모든 업무행에 `다음 행동`과 `선정 이유`가 있다.
- 신호 미검출을 안전으로 표시하지 않는다.
- 전체·부처별 화면 수치와 다운로드 수치가 일치한다.
- 원문 검수 결과가 저장·재로딩된다.

## 13. 이번 기획에서 하지 않은 것

- 현재 분석 코드와 대시보드는 아직 변경하지 않았다.
- 사업성격과 기대시차를 근거 없이 자동 확정하지 않았다.
- 새로운 정책 임계값을 임의로 만들지 않았다.
- 추가 외부 API나 LLM을 호출하지 않았다.
